# Week 2 — Views and Updateability

## A named query

A view presents the result of a query as a relation

```sql
CREATE VIEW active_student AS
SELECT student_id, name, major
FROM student
WHERE active;
```

Views support external schemas, reusable queries and restricted access to rows
or columns without duplicating the base data

## Virtual and materialised views

| Virtual view | Materialised view |
| --- | --- |
| Stores a definition | Stores query results |
| Reads current base data | May become stale |
| Pays query cost when read | Pays refresh cost when maintained |
| Uses little extra storage | Trades storage for faster reads |

Use a materialised view when an expensive result is read often enough to
justify refresh work

## Query modification

For a virtual view, the DBMS can replace the view reference with its defining
query and combine predicates

```sql
CREATE VIEW it_student AS
SELECT student_id, name, age
FROM student
WHERE major IN ('IT', 'MM');

SELECT name
FROM it_student
WHERE age > 19;
```

The effective base-table predicate is:

```sql
WHERE major IN ('IT', 'MM') AND age > 19
```

The real rewrite also has to preserve aliases, grouping, null semantics and
other SQL rules

## View maintenance

When base tables change:

- a virtual view needs no stored result update
- a materialised view needs a complete or incremental refresh
- indexes on a materialised view may also need maintenance

Incremental maintenance applies the effect of inserted, deleted or updated
base rows rather than recomputing the full result

## When a view can be updated

An update is safe only when the DBMS can map it to one unambiguous base-table
change

A simple single-table view is commonly updateable when it retains the key and
does not use aggregation, grouping, set operations or duplicate elimination

Views are commonly non-updateable when they contain:

- `GROUP BY` or aggregate functions
- `DISTINCT`, `UNION`, `INTERSECT` or `EXCEPT`
- a join where the target base row is ambiguous
- derived columns that cannot be assigned back to a base column

`WITH CHECK OPTION` prevents an update through a view from moving the row
outside the view predicate

```sql
CREATE VIEW it_student AS
SELECT student_id, name, major
FROM student
WHERE major = 'IT'
WITH CHECK OPTION;
```

> [!TIP] Decision rule
>
> Ask whether one visible row and column maps to exactly one base row and
> column, then check the actual DBMS rules

# Week 5 — Storage and File Organisation

## Why blocks dominate cost

Applications work with records but storage transfers pages or blocks between
secondary storage and memory

For a hard disk, a simplified access time is:

$$
T_{access}=T_{seek}+T_{rotation}+T_{transfer}
$$

Database cost models therefore count block I/O rather than individual field
comparisons

## Records inside blocks

For fixed-length unspanned records:

$$
bfr=\left\lfloor\frac{B}{R}\right\rfloor
$$

where $B$ is block size, $R$ is record size and $bfr$ is the blocking factor

For $r$ records, the required blocks are:

$$
b=\left\lceil\frac{r}{bfr}\right\rceil
$$

Spanned records may cross block boundaries while unspanned records leave any
remaining space unused

Variable-length records normally use a slot directory so records can move
inside a page without changing their external record identifier

## File organisations

| Organisation | Search strength | Update trade-off |
| --- | --- | --- |
| Heap | Full scans and fast inserts | Equality search may scan every block |
| Sequential | Ordered and range access | Inserts may require overflow or reorganisation |
| Hash | Equality search on the hash key | Poor ordering and range access |

### Heap file

Rows have no search-key order, so inserting into a page with free space is
cheap and a full scan is straightforward

A free-space list or page directory avoids searching every page for room

### Sequential file

Rows are stored in search-key order, enabling binary-style block search and
efficient ranges, but maintaining physical order makes arbitrary inserts more
expensive

### Hash file

A hash function maps a key to a bucket:

$$
bucket=h(key)
$$

A good function spreads records evenly, while collisions require overflow
space or another collision strategy

> [!TIP] Choose from the workload
>
> Heap suits scans and frequent inserts, sequential suits ordered ranges, and
> hashing suits equality predicates on a stable key

# Week 7 — Relational Algebra

Relational algebra is a closed algebra: every operator consumes relations and
produces a relation, so operators can be composed into a query tree

## Core operators

| Operator | Meaning | SQL analogue |
| --- | --- | --- |
| $\sigma_c(R)$ | Select rows satisfying $c$ | `WHERE` |
| $\pi_A(R)$ | Project attributes $A$ | `SELECT DISTINCT` |
| $\rho_S(R)$ | Rename a relation or attributes | `AS` |
| $R\times S$ | Cartesian product | `CROSS JOIN` |
| $R\cup S$ | Union | `UNION` |
| $R-S$ | Difference | `EXCEPT` |
| $R\cap S$ | Intersection | `INTERSECT` |

Union, difference and intersection require union-compatible relations with
matching arity and compatible attribute domains

## Selection and projection

For `ENROLMENT(student_id, course_id, mark)`:

$$
\pi_{student\_id}
\left(
\sigma_{course\_id='INFS2200'\land mark\ge50}(ENROLMENT)
\right)
$$

Selection keeps rows while projection keeps columns and removes duplicates
under pure relational semantics

## Joins

A theta join is a product followed by a selection:

$$
R\bowtie_c S=\sigma_c(R\times S)
$$

An equijoin uses equality conditions, and a natural join automatically matches
attributes with the same name while retaining one copy of each matched column

Outer joins retain unmatched tuples and pad missing attributes with nulls

## Division and “for all”

For $TAKES(student, course)$ and $REQUIRED(course)$:

$$
TAKES\div REQUIRED
$$

returns students related to every required course

Division corresponds to the same universal-quantification pattern often
written in SQL using double `NOT EXISTS`

## Translate a query systematically

For “names of students enrolled in INFS2200”:

$$
\pi_{name}
\left(
STUDENT\bowtie_{STUDENT.student\_id=ENROLMENT.student\_id}
\sigma_{course\_id='INFS2200'}(ENROLMENT)
\right)
$$

1. identify the relations that supply required attributes
2. create the join path
3. apply row conditions with selection
4. project only the requested output
5. rename when attribute names would be ambiguous

Equivalent expressions can produce the same result with very different
intermediate relation sizes, which motivates query optimisation

# Week 1 — DBMS Foundations, Dependencies and SQL

## Why a DBMS

A database management system places a controlled layer between applications
and persistent data

| Service | What it protects or enables |
| --- | --- |
| Integrity | Values and relationships remain valid |
| Reliability | Authorised users receive consistent results |
| Availability | Data remains usable when applications need it |
| Recoverability | Committed work survives faults |
| Shareability | Concurrent users work with common data |
| Scalability | Larger workloads remain manageable |
| Data independence | Storage changes do not force application rewrites |

SQL states **what** result is required while the DBMS chooses **how** to
retrieve it through storage, indexes and a query execution plan

## Functional dependencies

A functional dependency $X \rightarrow Y$ means that any two tuples agreeing
on the attributes in $X$ must also agree on the attributes in $Y$

For `ENROLMENT(student_id, course_id, student_name, grade)`:

$$
student\_id \rightarrow student\_name
$$

$$
(student\_id, course\_id) \rightarrow grade
$$

Dependencies describe the meaning of the data rather than a coincidence in
the current rows

### Keys and closure

The closure $X^+$ is the set of attributes functionally determined by $X$

1. begin with $X^+=X$
2. if $A\rightarrow B$ and $A\subseteq X^+$, add $B$ to $X^+$
3. repeat until no attribute can be added

$X$ is a superkey when its closure contains every attribute in the relation
and a candidate key when no proper subset of $X$ is also a superkey

## Normalisation checkpoint

Normalisation separates facts so that each fact is stored once

| Form | Main condition |
| --- | --- |
| 1NF | Every attribute value is atomic |
| 2NF | No non-key attribute depends on only part of a candidate key |
| 3NF | For every non-trivial $X\rightarrow A$, $X$ is a superkey or $A$ is prime |
| BCNF | For every non-trivial $X\rightarrow A$, $X$ is a superkey |

A useful decomposition should be lossless so joining the parts recreates the
original relation, and preferably dependency-preserving so constraints can be
checked without joins

## SQL query patterns

### Join related rows

```sql
SELECT s.name, e.grade
FROM student AS s
JOIN enrolment AS e USING (student_id)
WHERE e.course_id = 'INFS2200';
```

### Group, filter, then order

```sql
SELECT course_id, COUNT(*) AS enrolments
FROM enrolment
GROUP BY course_id
HAVING COUNT(*) >= 20
ORDER BY enrolments DESC;
```

`WHERE` filters rows before grouping while `HAVING` filters groups after
aggregation

### Express “all” with double `NOT EXISTS`

```sql
SELECT s.student_id
FROM student AS s
WHERE NOT EXISTS (
  SELECT 1
  FROM required_course AS r
  WHERE NOT EXISTS (
    SELECT 1
    FROM enrolment AS e
    WHERE e.student_id = s.student_id
      AND e.course_id = r.course_id
  )
);
```

Read this as “there is no required course for which no matching enrolment
exists”

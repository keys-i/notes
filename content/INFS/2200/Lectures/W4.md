# Week 4 — Database Constraints

## Legal states and transitions

| Constraint | Governs | Example |
| --- | --- | --- |
| Static | A valid database state | `quantity >= 0` |
| Dynamic | A valid change between states | A balance may fall by at most a daily limit |

Place an invariant in the database when every writer must obey it

## Declarative constraints first

```sql
CREATE TABLE enrolment (
  student_id bigint NOT NULL,
  course_id text NOT NULL,
  mark numeric(5, 2) CHECK (mark BETWEEN 0 AND 100),
  PRIMARY KEY (student_id, course_id),
  FOREIGN KEY (student_id) REFERENCES student(student_id)
);
```

| Constraint | Purpose |
| --- | --- |
| `NOT NULL` | Require a value |
| `CHECK` | Restrict values within one row |
| `UNIQUE` | Prevent duplicate candidate-key values |
| `PRIMARY KEY` | Identify each row and reject nulls |
| `FOREIGN KEY` | Require a matching referenced key |

Declarative constraints are visible to the optimiser, checked consistently
and usually clearer than procedural code

## Add and name constraints

```sql
ALTER TABLE enrolment
ADD CONSTRAINT enrolment_mark_range
CHECK (mark BETWEEN 0 AND 100);
```

Names make failures and later schema changes easier to understand

## Immediate and deferred checking

An immediate constraint is checked after each statement while a deferred
constraint is checked at transaction commit

```sql
SET CONSTRAINTS ALL DEFERRED;
```

Deferral is useful when intermediate states temporarily violate a relationship
but the transaction restores consistency before commit, and only constraints
declared deferrable can be deferred

## Triggers

A trigger runs in response to an event such as `INSERT`, `UPDATE` or `DELETE`

Use a trigger when an invariant depends on multiple rows, needs an audit event
or cannot be expressed declaratively

```sql
CREATE FUNCTION set_updated_at()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at := CURRENT_TIMESTAMP;
  RETURN NEW;
END
$$;

CREATE TRIGGER student_updated_at
BEFORE UPDATE ON student
FOR EACH ROW
EXECUTE FUNCTION set_updated_at();
```

Trigger code must account for multi-row statements, recursion, concurrency and
the difference between `OLD` and `NEW`

> [!WARNING] Avoid hidden business logic
>
> Prefer a key, `CHECK` or foreign key when it can express the invariant
> directly, then use the smallest trigger that closes the remaining gap

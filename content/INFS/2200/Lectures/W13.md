# Week 13 — Course Revision

## The inside-out story

```mermaid
flowchart LR
  Meaning[Dependencies and constraints] --> SQL[SQL and views]
  SQL --> RA[Relational algebra]
  RA --> Plans[Query plans]
  Plans --> Storage[Files and indexes]
  Storage --> TX[Transactions]
  TX --> CC[Concurrency control]
  CC --> Recovery[Logging and recovery]
```

The course connects logical meaning to physical execution and then protects
that execution under concurrency and failure

## Method-selection map

| If the question asks about | Start with |
| --- | --- |
| Redundancy or keys | Functional dependencies and attribute closure |
| Restricted or reusable data access | View definition and update mapping |
| Valid values or relationships | The narrowest declarative constraint |
| Block counts | Record size, blocking factor and ceiling operations |
| Access path | Predicate type, selectivity and file order |
| SQL meaning | A relational algebra tree |
| Faster execution | Cardinality reduction and physical alternatives |
| Schedule correctness | Conflicts, recoverability and precedence graph |
| Blocking or deadlock | Lock compatibility and wait-for graph |
| Crash recovery | WAL, checkpoint, commit state and steal/force policy |

## High-value distinctions

- a key identifies tuples while an index is a physical access structure
- a virtual view stores a query while a materialised view stores its result
- selectivity is a fraction while cardinality is a count
- conflict serialisability does not imply recoverability
- a precedence graph is not a wait-for graph
- steal determines the need for undo while no-force determines the need for redo
- WAL orders log persistence before affected data persistence

## Calculation checks

For each numerical storage or query-cost problem:

1. write units beside every value
2. distinguish records, blocks, bytes and I/O operations
3. apply floor to records per block and ceiling to blocks required
4. state distribution and buffering assumptions
5. compare alternatives using the same cost basis

## Schedule checks

1. preserve the order inside every transaction
2. mark conflicts only across different transactions on the same item
3. build all required edges before checking for a cycle
4. test recoverability separately from serialisability
5. apply the stated 2PL or timestamp rule one operation at a time

> [!TIP] Explain the reason
>
> A compact answer should name the rule, apply it to the given operations or
> data, and state the consequence

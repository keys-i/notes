# Week 6 — Database Indexing

## Indexes as access paths

An index is an auxiliary structure that maps a search-key value to a record or
block location

It can replace a full file scan with a much smaller search, but consumes space
and adds work to inserts, deletes and key updates

## Ordered-file indexes

| Index | Data-file order | Density | Pointer target |
| --- | --- | --- | --- |
| Primary | Primary key | Usually sparse | First block containing the key range |
| Clustering | Non-key ordering field | Usually sparse | First block for a value cluster |
| Secondary | Any non-ordering field | Usually dense | Record or list of matching records |

A sparse index has fewer entries than records and depends on the data-file
order, while a dense index has an entry for every record or distinct key value

## Multilevel indexes

If one index level is still large, build an index over that index until the top
level fits in one block

With fan-out $f$ and $N$ leaf blocks, the height grows approximately as:

$$
h\approx\lceil\log_f N\rceil
$$

Large fan-out keeps searches shallow

## B+ trees

A B+ tree is balanced and stores data pointers in the leaves

- internal nodes route searches
- every leaf is at the same depth
- linked leaves make range scans efficient
- insertion and deletion split, merge or redistribute nodes as needed

A point lookup follows one path from root to leaf, while a range lookup finds
the first key then follows leaf links

```sql
CREATE INDEX enrolment_course_idx
ON enrolment (course_id);
```

Composite index order matters: an index on `(course_id, student_id)` naturally
supports predicates beginning with `course_id`

## Hash and bitmap indexes

| Structure | Best fit | Weak fit |
| --- | --- | --- |
| Hash | Equality predicates | Ranges and ordering |
| Bitmap | Low-cardinality, read-heavy analytical data | Frequently updated transactional rows |
| B+ tree | Point, range and ordered access | Very low-selectivity predicates alone |

Bitmap indexes represent each distinct value with a bit vector, allowing fast
Boolean combinations such as `AND` and `OR`

## Index selection

Consider:

1. predicates and join keys used frequently
2. selectivity and data distribution
3. ordering and range requirements
4. write frequency and maintenance cost
5. whether an existing composite index already covers the access path

> [!WARNING] More is not always faster
>
> The optimiser may ignore an index when a large fraction of the table is
> needed, and every unnecessary index increases write and storage cost

# Week 12 — Database Recovery

## What recovery restores

Recovery supports atomicity by removing incomplete work and durability by
restoring committed work that had not reached the database files

- **undo** applies before-images in reverse log order
- **redo** applies after-images in forward log order

## Write-ahead logging

The log records transaction events and updates such as:

```text
<T1 start>
<T1, balance, 80, 60>
<T1 commit>
```

WAL requires the relevant log record to reach stable storage before the
corresponding changed page, and a commit record to reach stable storage before
commit is reported successful

## Steal and force

| Buffer policy | Consequence |
| --- | --- |
| Steal | An uncommitted dirty page may reach disk, so undo is needed |
| No-steal | Uncommitted pages stay off disk, so undo is unnecessary |
| Force | Every committed page reaches disk at commit, so redo is unnecessary |
| No-force | Committed pages may remain buffered, so redo is needed |

| Policy pair | Recovery work |
| --- | --- |
| Steal + no-force | Undo and redo |
| Steal + force | Undo only |
| No-steal + no-force | Redo only |
| No-steal + force | Neither for page updates |

Steal plus no-force is common because it supports large transactions and fast
commits, with WAL carrying the recovery burden

## Checkpoints

A checkpoint records a known recovery position and the transactions active at
that point, reducing how much log must be examined after a crash

A checkpoint is not a replacement for WAL and does not necessarily mean every
modern DBMS pauses all transaction work or flushes every page

## Recovery methods

### Deferred update

Database pages are not updated before commit, so uncommitted transactions need
no undo and committed updates after the checkpoint may need redo

### Immediate update

Pages may be written before commit, so recovery undoes incomplete transactions
and redoes committed changes when no-force is used

### Shadow paging

Updates go to new pages while a shadow page table retains the old committed
mapping, then commit switches the root pointer atomically

Shadow paging avoids log-based page undo but can cause copying, fragmentation
and concurrency limitations

## Crash-analysis checklist

1. identify the last relevant checkpoint
2. classify transactions as committed or incomplete at the crash
3. use the buffer policy to decide whether undo, redo or both are possible
4. undo losers backwards using before-images
5. redo winners forwards using after-images
6. make recovery actions idempotent so a second crash remains recoverable

# Week 11 — Concurrency Control

## Shared and exclusive locks

| Requested \ Held | Shared | Exclusive |
| --- | ---: | ---: |
| Shared | Compatible | Blocked |
| Exclusive | Blocked | Blocked |

A shared lock permits reading while an exclusive lock protects a write

Locking by itself does not guarantee serialisability because transactions can
acquire and release locks in unsafe orders

## Two-phase locking

Two-phase locking divides a transaction into:

1. a growing phase that acquires locks without releasing any
2. a shrinking phase that releases locks without acquiring new ones

2PL guarantees conflict serialisability, though it does not guarantee a
particular serial order and may deadlock

| Variant | Rule | Main effect |
| --- | --- | --- |
| Basic 2PL | No acquisition after first release | Conflict-serialisable |
| Conservative 2PL | Acquire all locks before execution | Avoids deadlock |
| Strict 2PL | Hold exclusive locks until commit or abort | Prevents dirty reads and cascading rollback |
| Rigorous 2PL | Hold all locks until commit or abort | Commit order matches serial order |

## Deadlock

A wait-for graph has one node per active transaction and edge
$T_i\rightarrow T_j$ when $T_i$ waits for a lock held by $T_j$

A cycle represents deadlock, which can be resolved by choosing a victim to
abort and later restart

Prevention schemes such as wait-die and wound-wait impose a consistent
timestamp priority so cycles cannot form

Livelock or starvation is repeated postponement without a cycle, so victim and
queue policies need fairness

## Timestamp ordering

Give each transaction timestamp $TS(T)$ and each data item:

- $readTS(X)$, the largest timestamp that successfully read $X$
- $writeTS(X)$, the largest timestamp that successfully wrote $X$

For `read(X)` by $T$:

- reject and restart if $TS(T)<writeTS(X)$
- otherwise permit it and update $readTS(X)$

For `write(X)` by $T$:

- reject and restart if $TS(T)<readTS(X)$ or $TS(T)<writeTS(X)$
- otherwise permit it and update $writeTS(X)$

Timestamp ordering avoids deadlock because transactions do not wait, but
repeated restarts can starve a transaction

> [!TIP] Keep the graphs separate
>
> A precedence graph tests a completed schedule for conflict serialisability,
> while a wait-for graph detects a current locking deadlock

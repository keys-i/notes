# Practical 6 — PostgreSQL Query Planning

## `EXPLAIN` versus `EXPLAIN ANALYZE`

`EXPLAIN` shows the chosen estimated plan without executing a `SELECT`

```sql
EXPLAIN
SELECT *
FROM DEPARTMENT
WHERE DEPTNO = 30;
```

`EXPLAIN ANALYZE` executes the statement and adds actual timing, row counts and
loop counts

```sql
EXPLAIN ANALYZE
SELECT *
FROM DEPARTMENT
WHERE DEPTNO = 30;
```

Important fields

| Field | Meaning |
| --- | --- |
| `cost=a..b` | Estimated startup and total cost in planner units |
| `rows` | Estimated result rows |
| `width` | Estimated average bytes per row |
| `actual time` | Measured startup and total time |
| `loops` | Number of node executions |
| `Planning Time` | Time spent choosing the plan |
| `Execution Time` | Time spent running it |

## Scan types

Without an index, the equality query uses a sequential scan and tests its filter
against each row

```sql
ALTER TABLE DEPARTMENT
ADD CONSTRAINT P_DEPTNO PRIMARY KEY (DEPTNO);
```

The primary key creates an index, allowing an `Index Scan` with
`Index Cond: (deptno = 30)`

A query that returns only indexed columns may use an `Index Only Scan`

```sql
SELECT DEPTNO
FROM DEPARTMENT
WHERE DEPTNO > 20 AND DEPTNO < 50;
```

`Heap Fetches` can still appear because PostgreSQL checks the table's visibility
map to decide whether each indexed row is visible to the current transaction

## Planner switches are experiments

```sql
SET enable_seqscan TO off;
```

This raises the estimated cost of sequential scans but does not make them
impossible when no other valid path exists

Disabling a scan type can produce a worse plan, especially for small tables, so
restore the normal setting after the experiment

```sql
SET enable_seqscan TO on;
```

## Join plan

```sql
EXPLAIN ANALYZE
SELECT E.ENAME
FROM EMPLOYEE AS E
JOIN DEPARTMENT AS D ON E.DEPTNO > D.DEPTNO
WHERE E.SAL > 1000;
```

The indexed practical plan uses

1. a sequential scan that filters `EMPLOYEE`
2. a nested loop over the qualifying employees
3. a memoised department lookup keyed by `E.DEPTNO`
4. an index-only scan for each uncached department range

`Memoize` avoids repeating the same lookup when many employees share a
department number

## Remove the index and compare

```sql
ALTER TABLE DEPARTMENT
DROP CONSTRAINT P_DEPTNO;
```

The primary-key index disappears with its constraint

The example plan then scans and materialises `DEPARTMENT`, performs many more
join comparisons and takes substantially longer on the supplied data

The comparison demonstrates causation better than an isolated fast or slow
number because the query and data remain fixed while the access path changes

## Checkpoint

- estimated and actual row counts are compared for large errors
- scan and join nodes match the predicates they serve
- loop counts are included when reading per-node timing
- planner settings are restored after testing
- the primary key is recreated if later work depends on it

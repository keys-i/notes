# Practical 5 — PostgreSQL Indexes

## Index trade-off

An index adds an access path that can avoid scanning every table row

It also consumes storage and must be maintained during inserts, deletes and key
updates, so an unused index is not free

## Measure before and after

The practical checks whether project leaders still exist in the employee table

```sql
SELECT COUNT(*)
FROM PROJECT AS P
WHERE EXISTS (
    SELECT 1
    FROM EMP
    WHERE EMPNO = P.PROJECTLEADER
);
```

Create the candidate B-tree index and rerun the same workload

```sql
\timing on
CREATE INDEX EMPNO_IDX ON EMP (EMPNO);
```

PostgreSQL may still choose a sequential scan when the index does not reduce
enough work, so a small timing change does not mean the index is broken

## Inspect indexes

The portable-looking `information_schema` does not expose every PostgreSQL
index detail, so catalogue views are useful here

```sql
SELECT INDEXNAME, INDEXDEF
FROM pg_indexes
WHERE TABLENAME = 'emp';
```

The `pgstattuple` extension exposes physical index information

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT TREE_LEVEL, LEAF_PAGES, INDEX_SIZE
FROM pgstatindex('empno_idx');
```

Remove an index when the experiment is finished

```sql
DROP INDEX EMPNO_IDX;
```

## Constraint-owned indexes

PostgreSQL automatically creates a unique B-tree index for a primary key

```sql
ALTER TABLE EMP
ALTER COLUMN EMPNO TYPE NUMERIC(9),
ADD CONSTRAINT EMP_PKEY PRIMARY KEY (EMPNO);
```

Do not add a duplicate manual index on the same leading columns without a
different demonstrated query need

## Expression indexes

An ordinary index on `EMPNO` does not directly serve a predicate on a transformed
value such as formatted text

```sql
SELECT COUNT(*)
FROM EMP
WHERE POSITION('000' IN TO_CHAR(EMPNO, 'FM000000000')) > 0;
```

The practical wraps the transformation in immutable functions, then indexes
the exact expression

```sql
CREATE INDEX EMP_EMPNO_FUNCTION_IDX
ON EMP (
    IPOSITION('000', ITO_CHAR(EMPNO, 'FM000000000'))
);
```

An index expression must be immutable because PostgreSQL assumes the same input
always produces the same indexed value

Confirm use with the actual plan

```sql
EXPLAIN ANALYZE
SELECT COUNT(*)
FROM EMP
WHERE IPOSITION('000', ITO_CHAR(EMPNO, 'FM000000000')) > 0;
```

The desired evidence is an `Index Scan` on
`emp_empno_function_idx`, not merely a faster result from a warmed cache

## Selection reminders

- high-cardinality identifiers suit a B-tree or hash access path better than a bitmap
- low-cardinality, read-heavy analytical columns are the classic bitmap case
- write frequency, selectivity and predicate shape all matter
- the optimiser decides whether an available index is worth using

## Checkpoint

- before and after measurements use the same data and query
- catalogue output identifies the owning constraint or manual index
- `EXPLAIN ANALYZE` confirms the access path
- timing is disabled with `\timing off` after the experiment

# Practical 2 — Constraints and Integrity

## Constraint roles

| Constraint | Invariant |
| --- | --- |
| `PRIMARY KEY` | Each row has a unique, non-null identifier |
| `CHECK` | A value satisfies a Boolean condition |
| `UNIQUE` | No two rows share the constrained value |
| `NOT NULL` | Every row supplies a value |
| `FOREIGN KEY` | A value refers to an existing parent row |

Start with a department table

```sql
CREATE TABLE DEPT (
    DEPTNO INTEGER,
    DNAME VARCHAR(14),
    LOCATION VARCHAR(13)
);
```

## Add named constraints

```sql
ALTER TABLE DEPT
ADD CONSTRAINT PK_DEPTNO PRIMARY KEY (DEPTNO);

ALTER TABLE DEPT
ADD CONSTRAINT CHK_DEPTNO
CHECK (DEPTNO > 9 AND DEPTNO < 100);

ALTER TABLE DEPT
ADD CONSTRAINT UN_DNAME UNIQUE (DNAME);

ALTER TABLE DEPT
ALTER COLUMN LOCATION SET NOT NULL;
```

Naming table constraints makes later inspection and removal direct

```sql
ALTER TABLE DEPT DROP CONSTRAINT UN_DNAME;
```

`NOT NULL` is stored as a column property, so it is set or removed through
`ALTER COLUMN` rather than `ADD CONSTRAINT`

## Inspect constraints

`information_schema` gives a portable view while `pg_constraint` exposes the
PostgreSQL definition

```sql
SELECT
    tc.constraint_name,
    tc.table_name,
    tc.constraint_type,
    pg_get_constraintdef(pc.oid) AS definition
FROM information_schema.table_constraints AS tc
JOIN pg_constraint AS pc
  ON tc.constraint_name = pc.conname
WHERE tc.table_name = 'dept'
  AND tc.constraint_schema = 'public';
```

Column-level `NOT NULL` does not appear as a named table constraint in this
result

## Test rejected data

Good tests include one row that violates each invariant

- a repeated `DEPTNO` should fail the primary key
- `DEPTNO = 9` should fail the range check
- a repeated `DNAME` should fail the unique constraint
- a missing `LOCATION` should fail `NOT NULL`

A failed insert is evidence that the database, rather than application code,
owns the rule

## Preserve relationships

```sql
ALTER TABLE EMP
ADD CONSTRAINT FK_DEPTNO
FOREIGN KEY (DEPTNO) REFERENCES DEPT (DEPTNO);
```

An employee cannot then reference a department that does not exist

Deletion policy is a separate design choice

```sql
ALTER TABLE EMP DROP CONSTRAINT FK_DEPTNO;

ALTER TABLE EMP
ADD CONSTRAINT FK_DEPTNO
FOREIGN KEY (DEPTNO) REFERENCES DEPT (DEPTNO)
ON DELETE CASCADE;
```

`CASCADE` prevents orphan rows by deleting dependent employees, but it is only
appropriate when deleting the parent should truly delete its dependants

## Limit of `CHECK`

A row-level `CHECK` cannot reliably enforce that an employee earns no more than
their manager because the rule compares different rows and must survive changes
to either row

That cross-row invariant needs a trigger or another transaction-safe design

## Checkpoint

- valid department and employee rows still insert
- every deliberate violation fails for the expected constraint
- catalogue output shows the named table constraints
- the chosen delete policy is tested rather than assumed

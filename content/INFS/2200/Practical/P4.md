# Practical 4 — Views and Materialised Views

## Regular views

A regular view stores a query definition rather than its result, so PostgreSQL
runs the underlying query whenever the view is read

```sql
CREATE VIEW V_EMP_ACC AS
SELECT EMPNO, ENAME, JOB, HIREDATE, SAL, DEPTNO
FROM EMP
WHERE DEPTNO = 30;
```

Query it like a table

```sql
SELECT * FROM V_EMP_ACC;
```

Simple single-table views can be updateable because PostgreSQL can map each
view row back to one base-table row

```sql
INSERT INTO V_EMP_ACC
    (EMPNO, ENAME, JOB, HIREDATE, SAL, DEPTNO)
VALUES
    (3035, 'NICK COLES', 'ENGINEER', '2015-01-01', 70000, 30);

UPDATE V_EMP_ACC
SET ENAME = 'JAMES ADAM'
WHERE EMPNO = 3035;
```

An aggregate view is not automatically updateable because one output row may
summarise many base rows

```sql
CREATE VIEW V_EMP_ACC AS
SELECT COUNT(*) AS EMP_COUNT, AVG(SAL) AS AVG_SAL
FROM EMP
WHERE DEPTNO = 30;
```

Use `INSTEAD OF` triggers only when a non-updateable view needs an explicit and
unambiguous write policy

## Materialised views

A materialised view stores the result of its query

```sql
CREATE MATERIALIZED VIEW MV_DEPT_SAL AS
SELECT
    DNAME,
    AVG(SAL) AS DSAL,
    MAX(SAL) AS DMAXSAL,
    MIN(SAL) AS DMINSAL
FROM EMP1
JOIN DEPT1 ON EMP1.DEPTNO = DEPT1.DEPTNO
GROUP BY DNAME;
```

Reads can be much cheaper because the join and aggregation were performed when
the materialised view was built

The trade-off is freshness

```sql
REFRESH MATERIALIZED VIEW MV_DEPT_SAL;
```

Changes to `EMP1` or `DEPT1` are not reflected until the refresh completes

## Compare behaviour

| Property | Regular view | Materialised view |
| --- | --- | --- |
| Stored object | Query definition | Query definition and result |
| Read freshness | Current base-table data | Last refresh |
| Read cost | Recomputes the query | Scans stored rows |
| Write path | Sometimes updateable | Refresh rather than direct update |
| Storage | Minimal | Result plus optional indexes |

Measure rather than assume the performance difference

```sql
\timing on
SELECT * FROM V_DEPT_SAL;
SELECT * FROM MV_DEPT_SAL;
\timing off
```

## Read the plans

```sql
EXPLAIN ANALYZE SELECT * FROM V_DEPT_SAL;
EXPLAIN ANALYZE SELECT * FROM MV_DEPT_SAL;
```

The practical's regular view expands into base-table sequential scans, a hash
join and a hash aggregate

The materialised view needs only a small sequential scan of its stored result

`EXPLAIN ANALYZE` executes the query, so use plain `EXPLAIN` for statements whose
effects should not occur during inspection

## Checkpoint

- the simple view reflects writes in its base table
- the aggregate view rejects ambiguous writes
- base-table changes leave the materialised result stale until refresh
- measured plans explain the timing difference

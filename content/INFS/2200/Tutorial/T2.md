# Tutorial 2 — Views

## Expand a view query

Given:

```sql
CREATE VIEW senior_student AS
SELECT student_id, name, major
FROM student
WHERE completed_units >= 32;
```

and:

```sql
SELECT name
FROM senior_student
WHERE major = 'CS';
```

Replace the view reference with its definition, preserve the projection and
combine predicates:

```sql
SELECT name
FROM student
WHERE completed_units >= 32
  AND major = 'CS';
```

## Classify the view

For each definition, ask:

1. is the result stored or recomputed
2. which base-table changes can affect it
3. can those changes be maintained incrementally
4. does one view row map to one base row
5. does every update target one real base column

An aggregate view such as totals by course is useful for reads but does not
provide an unambiguous target row for ordinary updates

## Materialisation trade-off

Estimate:

- read frequency and query cost saved
- update frequency and refresh cost added
- acceptable staleness
- storage and index overhead

Materialisation is a workload decision rather than a property that always
makes a view faster

# Tutorial 11 — Concurrency Control

## Simulate 2PL

Keep a table with the lock owner, mode and waiting queue

| Step | Request | Decision |
| ---: | --- | --- |
| 1 | $T_1:S(X)$ | Grant |
| 2 | $T_2:X(X)$ | Wait for $T_1$ |
| 3 | $T_1:X(Y)$ | Grant |

Mark the first unlock because a basic 2PL transaction may acquire no new locks
after that point

## Build a wait-for graph

Add edge $T_i\rightarrow T_j$ only while $T_i$ is blocked by a lock held by
$T_j$

Remove the edge when the lock is granted or a transaction ends, and treat a
cycle as a current deadlock rather than a serialisability result

## Apply timestamp ordering

For each successful operation, update the item's timestamps immediately

| Operation | Reject when |
| --- | --- |
| `read_T(X)` | $TS(T)<writeTS(X)$ |
| `write_T(X)` | $TS(T)<readTS(X)$ or $TS(T)<writeTS(X)$ |

On rejection, restart according to the stated policy and do not continue using
effects from the rejected attempt

## Compare the protocols

| 2PL | Timestamp ordering |
| --- | --- |
| Transactions may wait | Transactions restart instead of waiting |
| Deadlock is possible in common variants | Deadlock is absent |
| Lock management costs memory and coordination | Restarts can waste completed work |
| Strict variants simplify recovery | Basic rules may need additional recoverability controls |

# Tutorial 8 — Query Processing

## Compare complete plans

Suppose $R$ uses 200 blocks and $S$ uses 40 blocks

A one-block nested loop with $R$ outer costs roughly:

$$
200+(200\times40)=8200
$$

With $S$ outer:

$$
40+(40\times200)=8040
$$

The difference is modest in this simplified version, while a multi-buffer
block nested loop can reduce repeated inner scans substantially

## Selection before join

If a predicate reduces $R$ from 200 blocks to 10 temporary blocks, joining the
filtered input can save far more I/O than changing only the join orientation

This is why a valid comparison includes the cost of producing each input, not
just the join operator

## Plan-reading worksheet

For every node, record:

| Question | Evidence |
| --- | --- |
| What rows enter | Child cardinality |
| What operation runs | Scan, filter, sort, hash or join |
| What rows leave | Estimated and actual cardinality |
| How often it runs | Loop count |
| What resource dominates | I/O, CPU or memory |

## Algorithm choice

- index nested loop when the outer side is small and the inner probe is cheap
- hash join for a large equijoin without useful ordering
- sort-merge when sorted inputs exist or ordered output is valuable
- scan when most blocks are needed regardless of index availability
